# Architecture Overview

## Purpose

The Vehicle Management System is a multi-tenant fleet operations platform. It starts as a domain-driven modular monolith: one deployable API owns transactional workflows, while separately deployable web and worker processes share contracts and infrastructure packages. This keeps early operations simple while preserving boundaries for later extraction.

Milestone 1 adds the identity and organization foundation. Vehicle, driver, trip, maintenance, and other fleet domains remain outside the current boundary.

## Repository topology

```text
apps/
  api/             NestJS REST transport and composition root
  web/             Next.js management application
  worker/          NestJS background-process composition root
packages/
  config/          Runtime environment parsing and validation
  contracts/       Transport-neutral request/response contracts
  database/        Prisma schema, migrations, client factory
  observability/   OpenTelemetry-compatible bootstrap helpers
  ui/              Shared React UI primitives
  validation/      Shared validation helpers
docs/
  adr/             Accepted architectural decisions
  architecture/    Living architecture documentation
```

Applications may depend on packages. Packages must not depend on applications. Domain modules introduced later will live under `apps/api/src/modules/<module>` and keep explicit `domain`, `application`, `infrastructure`, and `transport` folders. A module may consume another module only through an exported application contract or event, never by reaching into its persistence implementation.

## Runtime processes

- `web` serves the browser management interface and calls versioned REST endpoints.
- `api` exposes `/api/v1`, validates requests, establishes trusted request context, invokes use cases, and maps results to HTTP.
- `worker` claims and publishes transactional outbox events through an abstract publisher.
- PostgreSQL is the authoritative transactional store.
- Redis is reserved for ephemeral caching, rate limits, distributed locks, idempotency, and worker coordination.
- S3-compatible storage holds binary objects. Local development uses MinIO.

Telemetry, notifications, integrations, and analytics remain modules initially but are likely extraction candidates. No Kafka, Kubernetes, Elasticsearch, or warehouse is part of the foundation.

## Backend dependency rule

```text
HTTP / event transport
        |
        v
application use cases
        |
        v
domain model ------> repository interfaces
                         ^
                         |
                infrastructure adapters
```

The composition root wires implementations to interfaces. Domain and application layers do not import NestJS controllers, Prisma models, Redis clients, cloud SDKs, or UI types. Transactions are owned by application operations. Lifecycle entities expose controlled transitions and protect invariants.

## Multi-tenancy and security

`organization_id` is the tenant boundary for organization-owned records. A bearer token establishes the user, while `x-organization-id` only proposes a tenant. The API validates active user, organization, and membership records before creating trusted request context. Route organization IDs must equal that context; request bodies and query strings never establish it.

Permission-based RBAC grants permission codes through organization-scoped roles. Composite foreign keys prevent cross-tenant role assignment. The local JWT adapter is limited to development and automated tests; a future OIDC/JWKS adapter plugs into the provider-neutral authentication port.

## API conventions

- All public endpoints are versioned under `/api/v1`.
- OpenAPI is generated by the API application.
- Inputs are rejected when unknown or invalid.
- Errors use a stable structured shape and include a request ID once request context is introduced.
- List endpoints will use cursor or bounded page pagination, explicit sorting, and allow-listed filters.
- Domain transitions use action endpoints such as `POST /trips/{id}/start`.

`GET /api/v1/health` remains public. Identity discovery uses `GET /api/v1/organizations` and tenant-scoped `/me`. Organization, membership, role assignment, and audit endpoints live below `/api/v1/organizations/{id}` and require documented permissions.

## Events and consistency

Consequential mutations persist business data, immutable audit data, and an outbox event in one PostgreSQL transaction. The worker claims with row locking and a lease, retries with backoff, and publishes at least once. Event UUIDs are stable idempotency keys; consumers must deduplicate. Redis never becomes a system of record.

## Observability

Each process initializes OpenTelemetry-compatible tracing before application bootstrap. Console export is opt-in for local diagnosis. Production exporters are configured through standard OTLP environment variables. Health endpoints, structured logs, metrics, and trace correlation will be expanded alongside operational features.

## Testing strategy

- Domain and application logic: fast unit tests without NestJS or infrastructure.
- Infrastructure: integration tests against disposable PostgreSQL/Redis/object storage.
- Transport: API tests that exercise validation, authorization, and error mapping.
- Browser: Playwright for critical user workflows.
- Security: explicit permission and tenant-isolation suites beginning in Milestone 1.

CI runs formatting, linting, type checking, unit/integration tests, production builds, and browser smoke tests. Database migrations are applied to a clean PostgreSQL service in CI.
